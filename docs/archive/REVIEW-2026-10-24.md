# Architecture and code review — 24 October 2026

## Requested contract

The developer can edit/create/delete/rename normally. AI cannot change locked files or descendants of locked folders until explicit human unlock. Policy must stay on this machine and have no effect on collaborators pulling a repository.

The existing extension cannot deliver the universal AI-only contract. Ordinary VS Code extensions and terminal processes can share the developer's authority, while file events cannot authenticate AI origin. This review does not certify strict enforcement.

## Findings and changes

| Finding | Effect | Current change |
| --- | --- | --- |
| chmod, immutable flags and editor read-only rules applied globally to a resource | Human edits blocked too | Normal locks no longer apply OS/editor read-only controls; recorded legacy controls are restored |
| Automatic instruction/settings writes inside repositories | Policy could reach collaborators through Git | New locks write only machine-local policy; existing instruction files preserved |
| Workspace-only policy | Opening a project from another context lost the apparent lock | Absolute-path policy shared across local windows of one profile |
| Concurrent read/modify/write operations | Lock updates could overwrite each other | Atomic file persistence and cross-window transaction lease |
| Lock/snapshot/instruction failures coupled | UI could indicate protection after a partial failure | Policy persistence is the lock operation; commands return actual errors |
| Invalid stored manifest silently became empty | Protected state silently disappeared | Invalid or unexpectedly missing local policy stops evaluation |
| Parent delete/rename ignored locked children | A protected child could be destroyed through its ancestor | Destructive operations check locked descendants |
| Broker checked lexical containment only | Symlinks could escape original or staging roots | Existing path components reject symlinks/junctions |
| Copy taken before a second baseline inventory | Concurrent developer edits could become a false baseline | Baseline now describes the delivered staging copy |
| Fixed temporary filenames and replacement mode | Collisions and lost executable bits | Unique exclusive temporary writes; retain original permission bits |
| One audit failure poisoned the queue | Later events could never be logged | Queue recovers on later writes |

| Review session existed only in memory | Reload lost the active session | Session retained in local workspace state |

## Verification

Validated locally on macOS: 30 unit/service tests and 9 isolated VS Code Extension Host tests. TypeScript checks pass; production-dependency audit reports zero vulnerabilities. No Linux/Windows or hostile-agent enforcement certification is implied.

Unit/service regressions cover persistence, cross-window updates, current-policy lock/unlock, folder descendants, hard-link aliases, parent operations, symlink/traversal escape attempts, concurrent developer edits, corrupted/removed policy, transaction exceptions, permission preservation and audit recovery.

Isolated VS Code tests cover manual editor saves and filesystem writes while policy-locked, repeated lock/unlock, multi-selection, deleted targets, outside-workspace targets, strict-mode errors, local-only artifacts and legacy settings cleanup. Test profiles are temporary and separate from the developer's installed extensions.

The previous 0.8 tests proved normal write denial for humans and AI together. They did not establish AI-only prevention. Current tests explicitly distinguish broker policy from unavailable external-agent enforcement.

## Required next architecture

Keep the human editor and its source filesystem outside the agent boundary. A trusted local service owns policy, authenticates unlock, confines agent runtimes and their descendants, and applies allowed proposals through native filesystem operations. Agent extensions running in the human's shared host must move into a restricted environment or supply a verified integration controlling every write route.

Cooperative instructions, hooks, watcher rollback, process-name guesses and another chmod pass do not supply that authority boundary. This is additional runtime/service work, not a lock-icon fix.

## Release status

Review build only. macOS tests do not certify Linux/Windows, hostile-process TOCTOU resistance, lease recovery after a crash, native sandboxing or installed-profile upgrade acceptance. See RELEASE.md and SECURITY.md for remaining work. Do not market this build as automatic protection from every AI.
